## Findings

### 집계 관점

**F1. D/E 러너 비대칭 — E에서 해결한 검증이 D에는 없다 (fix-now).**
`strategy_e.py`가 세운 계약(무효 OHLCV 구간 분리, dictionary 순서 무관 fingerprint, timezone bound 검증, zero-trade CSV 헤더, CLI 테스트)이 `strategy_d.py`에는 없다. 이는 스토리 6-1(D 최초 구현)에서 만든 코드를 6-2(E)가 비대칭적으로 보강했고, D로 소급되지 않은 교차 스토리 결함이다.
- D는 `window.loc[valid_rows]`로 무효 행을 제거한 뒤 *이어 붙여* 시그널·엔진을 실행한다(`strategy_d.py:247-266`) — 반면 `strategy_api.py:212`(6-4)의 D/E는 `_valid_segments`로 구간 분리해 계산한다. 즉 **D 러너의 baseline이 6-4 API와 같은 데이터에 대해 어긋날 수 있다.** E는 `_valid_segments`를 사용한다(`strategy_e.py:321-333`).
- D의 `data_fingerprint`는 `data.items()`(정렬 안 됨) + 라벨 길이 미기록 + **윈도우 적용 후** 프레임 해시(`strategy_d.py:261-263`). E는 `sorted(data)` + 길이 prefix + 전체 프레임(윈도우 무관) 해시(`strategy_e.py:301-310`). D fingerprint는 실행 구간·딕셔너리 순서가 바뀌면 바뀐다 — "재현성" 주장과 모순. 이 차이는 6-8에서 이미 defer로 기록됐다(`spec-6-8:13-27`) — D/E의 서로 다른 실행에서 E fingerprint가 동일(`b2e027e0...`, `backtest-baseline.md:168-169`)하게 나온 데서도 재현됨.
- D CLI는 zero-trade 시 헤더 없는 빈 CSV를 쓸 수 있다(`strategy_d.py:327` vs `strategy_e.py:404-406`). D `main()`은 테스트 0건(`test_strategy_d.py`에 `main()`/argv 호출 없음), E는 CLI 테스트 존재(`test_strategy_e.py:472`).
- D는 tz 불일치 bound를 원시 pandas TypeError로 중도 실패시키고(`strategy_d.py:232-252`), E는 사전 검증 ValueError를 낸다(`test_strategy_e.py` tz-mismatch 테스트).

**F2. TP/SL/cutoff 파라미터 3중 원천 + 상호 parity 부재 (fix-now).**
같은 수치가 Python dataclass(`strategy_d.py:49`, `strategy_e.py:50`), `strategy_api.py:24-43`의 `_STRATEGY_PARAMS`, SQL `outcome_strategy_rules`(`202609051600_parameterize_outcome_strategy_rules.sql:19-26`)에 각각 하드코딩돼 있고, 각 층 테스트는 자기 자신을 기준으로만 검증한다. `grep outcome_strategy_rules --include=*.py` → 0건으로 Python과 SQL 규칙이 연결되는 테스트가 없다. 파라미터 한쪽이 바뀌면 운영 OPEN 스냅샷과 백테스트가 조용히 어긋난다.

**F3. review-patch migration 5개가 같은 guard를 여러 번 다시 쓰고 의미가 전환됨 (defer/문서화).**
`202609051700`~`202609052100` 다섯 migration이 `guard_outcome_strategy_snapshot`을 `create or replace`로 3회 재정의하며 A/B/C cutoff 고정↔해제, 미등록 전략 raise↔passthrough 등 의미가 뒤집힌다. `051700`과 `052000`은 파일명 slug가 같고(`harden_outcome_strategy_snapshot_contract`), `052000`이 `051700`이 만든 제약 이름을 drop·재정의한다. 미완전 적용된 운영 DB는 어느 세대 guard를 갖고 있는지 판별이 어렵다. (26-5로 forward-only라 과거는 불변; 재발 방지 정책 제안)

**F4. outcome_strategy_rules에 감사 가능한 수정 경로가 없다 (accept — 설계대로, 운영 리스크 기록).**
규칙 테이블은 `grant select ... to service_role`뿐이라(`202609051600:28-30`) 변경은 psql/migration으로만 가능하고 감사 경로가 없다. 스토리 6-5 리뷰가 "고정 seed·service-only 권위 계약"으로 기각한 범위(`spec-6-5:100`)이므로 의도된 설계로 수용하되, 운영 TP/SL 변경 시 감사 흔적이 없다는 리스크는 열린 상태로 남긴다.

**F5. `publish_attempt`가 단일 OPEN 실패에 전체 close 배치를 롤백한다 (defer).**
`202609051600:289-295`의 루프가 `emit_open_command`를 예외 처리 없이 호출해, 한 종목의 `MISSING_DAILY_OHLCV_CLOSE`/규칙 누락이 종목 전체 배치를 원자적으로 실패시킨다. 기존 Epic 3 동작 범위이며 이번 확장이 만든 회귀는 아니므로 defer 기록.

**F6. 골든 픽스처 E가 단일 종목 — Jaccard 게이트가 binary (accept, 문서화).**
`tests/fixtures/golden/golden_signals.json`의 E 시그널은 1종목뿐(백테스트 실행 기준 A 23·B 32·C 12·D 3·E 1, `spec-6-4:112`). 신호 빈도가 실제로 낮아지므로 대표성 한계가 관측치 그대로다. E 회귀 게이트가 사실상 1종목 정렬 검사임을 문서로 남긴다.

**F7. `strategy_api` 짧은 프레임 분류 전환: INELIGIBLE → ERROR (accept — 의도된 개선, 부작용 기록).**
`strategy_api.py:198-210`에서 `_invalid_frame_reason` 검증이 이력 길이 판정보다 먼저 수행돼, 120일 미만+malformed 프레임이 `INELIGIBLE` 대신 `ERROR`로 분류된다. 이는 6-4 리뷰가 "짧은 malformed 입력의 INELIGIBLE 오분류"로 지적해 의도적으로 변경한 것이며(`spec-6-4:92`), tags_stage의 ineligible/error 계수 의미가 달라지는 부작용이 있다.

**F8. spec 번호 불일치 — epics.md의 "Story 6.7" 중복 (fix-now, 문서 정정).**
`epics.md:1791`(UI 확장)과 `epics.md:1815`(OOS 검증)가 둘 다 "### Story 6.7"이며, OOS는 실제로 6.8로 구현됐다(`spec-6-8`). 계획 문서의 번호 체계가 구현과 어긋나 이후 참조·추적을 헷갈리게 한다.
