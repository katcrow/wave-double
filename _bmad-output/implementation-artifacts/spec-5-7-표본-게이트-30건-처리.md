## Intent

**Problem:** 5-5(전체)·5-6(전략×source) view는 표본 크기와 무관하게 항상 승률·PF 수치를 반환한다. 종결 건수가 적을 때(예: 8건) 잡음 수준의 승률을 실제 신호로 오인할 위험이 있고, Metric comparison(5.12)이 전략별/전체를 토글할 때 참조할 "전략별 + 전체" 단일 view가 아직 없다.

**Approach:** `candidate_outcome`에서 `strategy`의 `rollup`으로 전략별 + 전체(strategy IS NULL) 행을 한 번에 반환하는 신규 versioned view `candidate_outcome_win_rate_pf_by_strategy_gated`를 추가한다. 종결(TP+SL+TIMEOUT) 건수가 30 미만이면 `win_rate`/`profit_factor`를 NULL로, `sample_gate_passed=false`와 `표본 부족 (n/30)` 라벨을 반환한다. 종결/진행중 카운트는 게이트 상태와 무관하게 항상 채워진다.

## Boundaries & Constraints

**Always:**
- 산식·분모 규칙은 5-5와 완전 동일(TP/SL/TIMEOUT 분모, 승패는 return_pct 부호, OPEN/SUSPENDED/DELISTED 별도 카운트, 반올림 4자리).
- `group by rollup(strategy)`로 전략별 행 + 전체 합계 행(strategy IS NULL)을 한 view에서 반환한다. 별도 "전체 전용" view를 새로 만들지 않는다(5-5 view는 그대로 두고 변경하지 않는다).
- 게이트 임계값은 상수 30(`sample_gate_min_required`)이며 컬럼으로 노출한다. `sample_gate_passed = (total_settled >= 30)`.
- 게이트 미충족 시 `win_rate`/`profit_factor`만 NULL로 대체하고 `sample_gate_label`에 `표본 부족 (n/30)`(n=실제 total_settled)을 채운다. 충족 시 `sample_gate_label`은 NULL.
- `total_settled`/`wins`/`losses`/`open_count`/`suspended_count`/`delisted_count`/`gross_win`/`gross_loss`는 게이트 상태와 무관하게 항상 산식대로 채운다(숨기지 않는다) — "진행중 m건"이 항상 함께 노출돼야 하므로.
- migration은 forward-only(AD-14). `create or replace view` + `comment on view/column` + `revoke select ... from public, anon, authenticated`(5-5/5-6과 동일 패턴).
- 동일 fixture로 JSON↔SQL INSERT↔SQL rollup 기대값↔Python 기준값 4중 동등성 검증(AD-8). 경계값(정확히 29건 vs 30건)을 fixture에 포함해 게이트 boundary를 직접 검증한다.
- 운영 Supabase MCP로 migration 적용 + SQL fixture 검증 + `production_parity_baseline.json` 갱신.

**Never:**
- 5-5(`candidate_outcome_win_rate_pf`)·5-6(`candidate_outcome_win_rate_pf_by_strategy_source`) view를 수정하지 않는다.
- source 분해를 이 view에 포함하지 않는다(원천 필터는 Story 5.14 소관, epic-5-context.md Cross-Story Dependencies).
- 95% 신뢰구간·이탈 임계값·기대치 대조 판정 로직을 여기서 구현하지 않는다(Story 5.8/5.9 소관). 이 view는 게이트 boolean/라벨만 반환한다.
- UI 변경 없음(계산은 view가 전담, AD-8).

## Design Notes

### view 정의 (`candidate_outcome_win_rate_pf_by_strategy_gated`)

```sql
create or replace view public.candidate_outcome_win_rate_pf_by_strategy_gated as
with base as (
  select
    strategy,
    count(*) filter (where status in ('TP','SL','TIMEOUT')) as total_settled,
    count(*) filter (where status in ('TP','SL','TIMEOUT') and return_pct > 0) as wins,
    count(*) filter (where status in ('TP','SL','TIMEOUT') and return_pct < 0) as losses,
    count(*) filter (where status = 'OPEN') as open_count,
    count(*) filter (where status = 'SUSPENDED') as suspended_count,
    count(*) filter (where status = 'DELISTED') as delisted_count,
    sum(return_pct) filter (where status in ('TP','SL','TIMEOUT') and return_pct > 0) as gross_win,
    abs(sum(return_pct) filter (where status in ('TP','SL','TIMEOUT') and return_pct < 0)) as gross_loss
  from public.candidate_outcome
  group by rollup(strategy)
)
select
  strategy,
  total_settled, wins, losses, open_count, suspended_count, delisted_count,
  gross_win, gross_loss,
  case when total_settled >= 30
    then round(wins::numeric / nullif(total_settled, 0), 4) end as win_rate,
  case when total_settled >= 30
    then round(gross_win / nullif(gross_loss, 0), 4) end as profit_factor,
  30 as sample_gate_min_required,
  (total_settled >= 30) as sample_gate_passed,
  case when total_settled < 30
    then '표본 부족 (' || total_settled || '/30)' end as sample_gate_label
from base;
```

- `strategy IS NULL` 행 = 전체(rollup 합계). 5-5 view와 분모 규칙은 동일하지만 **별도 view**(5-5 대체 아님, UI가 5-5/5-6/이 view를 각자의 용도로 계속 사용).
- fixture 경계값: 전략 X는 정확히 29건(게이트 실패), 전략 Y는 정확히 30건(게이트 통과) — 정수 하나 차이로 승률/PF 노출 여부가 갈리는 것을 직접 증명한다.
- revoke는 5-5/5-6과 동일: `revoke select on table ... from public, anon, authenticated;`.

2. **마이그레이션 컬럼 주석 부정확 (blind-hunter 제기).** `candidate_outcome_win_rate_pf_by_strategy_gated.profit_factor` 주석이 "gross_loss가 0이면 NULL"이라고 적었지만, 실제로는 `sum(...) filter(...)`가 해당 부호 거래가 없을 때 `NULL`을 반환하는 것이지 `0`을 반환하는 게 아니다(`nullif(gross_loss,0)`은 리터럴 0 방어용 가드일 뿐). forward-only(AD-14) 원칙에 따라 view 정의는 그대로 두고 신규 마이그레이션 `infra/supabase/migrations/202609101400_fix_gated_profit_factor_comment.sql`로 `comment on column`만 정정해 운영에 적용, `col_description()`으로 반영 확인.

**defer (별도 항목으로 이관, `deferred-work.md` 등록):**

3. **`tools/production_parity_baseline.json`에 이 스토리와 무관한 사전 drift가 섞여 들어감 (3개 레이어 모두 독립적으로 제기).** `write_stage` 함수의 `search_path`가 `"public"` → `"pg_catalog"`로 baseline이 갱신됐는데, 이 스토리의 마이그레이션은 `write_stage`를 전혀 건드리지 않는다. 운영 DB에 직접 쿼리해(`pg_proc.proconfig`) 실제 운영 값이 이미 `pg_catalog`임을 확인 — 즉 이전 스토리에서 발생한 사전 drift가 이번 `--write-baseline` 갱신 과정에서 함께 포착된 것이며, 이 스토리가 만든 회귀가 아니다. 별도로 검토할 가치가 있어 defer.

**dismiss (조사 후 근거 있는 기각):**
