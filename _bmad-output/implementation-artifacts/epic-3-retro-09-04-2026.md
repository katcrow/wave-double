## Findings

### 핵심 수용 차단 항목

1. **[high] 운영 migration/function drift** — 저장소에 있는 3.2~3.10 migration과 운영 catalog가 일치하지 않는다. `list_migrations`에는 3.1 기본 schema 이후 항목이 없고, 대상 RPC도 모두 0건이다. 저장소 fixture와 local build가 통과해도 운영 자동 적재 경로가 호출될 수 없다. `fix now`가 필요한 운영 배포/검증 항목이나, 이번 회고에서는 production DDL을 임의 적용하지 않고 rejected로 판정한다.

2. **[high] Epic acceptance와 story scope의 충돌** — Epic 3.5는 SUSPENDED GitHub Issue 생성·close·14일 escalation을 요구하고(`epics.md:912-931`), 3.9는 LS status 기반 자동 DELISTED 감지와 능동 알림을 요구한다. 반면 3.5/3.9 story spec은 이를 “Neo 결정으로 이번 story에서 구현하지 않음”으로 명시한다. 이는 구현 누락이라기보다 승인된 범위 결정과 상위 acceptance의 불일치이며, correct-course 또는 명시적 Epic AC 변경 없이는 완료 판정을 내릴 수 없다.

### bmad-review triage

adversarial, edge-case-hunter, verification-gap 렌즈로 diff 범위를 다시 읽었다. 구체 후보 12건을 만들고 spec/코드/fixture/운영 catalog로 재검증한 결과는 다음과 같다.

3. **[medium, defer]** `daily_ohlcv.close`가 0/음수를 허용해 pricechk가 없고 전일 종가가 0인 경우 3.5 fallback이 조용히 감지를 건너뛴다. `202609021500_create_daily_ohlcv.sql`과 3.5의 `v_prev_close <> 0` guard에 근거하며, Story 2.1 schema ownership으로 이관한다.

4. **[medium, defer]** 동일 logical run/ticker/strategy에 두 번째 CORRECTION을 남길 때 shared unique index가 raw `unique_violation`을 낸다. 여러 correction을 새 event로 허용할지 idempotent하게 할지 설계 결정이 필요하다(`spec-3-8` deferred).

5. **[medium, defer]** correction이 다른 OPEN과 충돌하는 경우 도메인 오류로 정규화하지 않고 unique constraint 오류가 노출된다. 데이터 무결성은 보존되지만 운영자 오류 계약이 일관되지 않다.

6. **[low, defer]** terminal에서 SUSPENDED로 correction할 때 exit_date/exit_price/return_pct를 자동 null 처리하지 않는다. 현재 AC는 SUSPENDED→OPEN 복귀만 정의하므로 향후 correction 상태 전이 정책을 확정해야 한다.

7. **[low, defer]** correction API에 entry_date 정정 파라미터가 없다. entry_date가 잘못 적재된 경우 자연키·cutoff 기준을 함께 복구할 명시 경로가 없다.

8. **[low, defer]** `emit_open_command`는 ticker/strategy 행 잠금, correction은 outcome_id 잠금을 사용해 드문 동시 실행에서 unique violation으로 실패할 수 있다. 트랜잭션 rollback으로 손상은 막지만 lock protocol이 통일되지 않았다.

9. **[low, defer]** publish_attempt의 SUSPENDED/TP/SL/TIMEOUT update가 version을 증가시키는지 직접 assertion이 없다. trigger 정의로 구조상 보장되지만 회귀 fixture의 직접 증명이 필요하다.

10. **[low, defer]** `tests/fixtures/outcome_rebuild/*.json`과 SQL fixture의 데이터가 별도 관리되어 drift 가능성이 있다.

11. **[low, defer]** CI SQL fixture 목록이 `.github/workflows/test.yml:108`에 수동으로 하드코딩되어 신규 fixture가 목록에 빠질 수 있다.

12. **[low, accept as-is]** `outcome_events_open_command_key_idx`라는 이름이 OPEN 외 SUSPENDED/TP/SL/TIMEOUT/CORRECTION에도 재사용된다. 기능 결함은 아니며 migration rename의 운영 위험이 이득보다 커 현재는 그대로 둔다.

다음 후보는 반증 또는 명시적 설계로 dismiss했다.

- rebuild가 `outcome_observations`를 projection 계산에 사용하지 않는 점은 spec 3.10이 관찰을 판정 근거 장부로만 두고 이벤트를 유일한 projection source로 명시한다.
- 동일 timestamp event를 `event_id`로 tie-break하는 점은 현재 spec이 결정적 정렬을 명시한 결과다. 다만 실제 append 순서와 동일하다는 증명은 아니므로 향후 event ordering 설계에서 재검토할 수 있다.
- 3.9의 자동 감지/알림 미구현은 story spec에 명시된 범위 결정이라 해당 story 단독 결함으로는 dismiss했지만, 상위 Epic acceptance와의 충돌은 핵심 finding 2로 남겼다.
- Playwright smoke 미실행은 Epic 3 diff가 DB/batch 계층이고 UI surface를 변경하지 않았기 때문이며, 프론트엔드 회고 항목으로 오인하지 않았다.

## Acceptance verdict

**Rejected.**
