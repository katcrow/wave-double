## 1. Vision

Neo는 백테스트로 검증해 확정한 **6종 매수 전략(A·B·C·D·E·F)**을 보유하고 있습니다. A/B/C는 73개월·104종목 데이터에서 승률 66~69%, PF 1.82~2.08을 기록했습니다. D(돌파3%기법)는 승률 83.1%(총거래 77건), E(익절2%_고정SL5%기법)는 승률 78.2%·PF 1.34(총거래 78건)를 기록했다(2026-09-04 Correct Course로 V1 편입, §7 참조). F(각도 가속·이평선 쌍바닥 기법)는 승률 70.10%·PF 1.6585(총거래 194건)를 기록했다(2026-09-07 Correct Course로 V1 편입, §7 참조). 하지만 이 우수한 전략을 **매일 종목 발굴**로 옮기는 과정이 수동·비체계적이었습니다. `screen_abc.py`를 직접 실행하고 CSV를 열어보는 방식이라, 조건검색식이 뽑은 후보 모집단과 실제 전략 시그널이 맞닿는 순간을 놓치기 쉽고, 종목별·시장 전체의 수급(외인/기관/개인/프로그램) 데이터는 여러 API에 분산되어 있어 한눈에 파악하기 어려웠습니다.

wave-double은 이 고통을 해소합니다. 매 거래일(및 장중 30분 간격) 자동 실행되는 파이프라인이 조건검색식 후보 모집단을 갱신하고, 그 위에 전략 A/B/C 시그널을 계산해 **태깅된 후보만** 노출하며, 각 후보의 2일전/1일전/당일 수급·가격 데이터와 시장 전체 수급을 하나의 대시보드에 모아줍니다. Neo는 매일 아침 대시보드 하나로 "오늘 후보는 누구, 어떤 전략으로, 수급은 어떤지"를 5분 안에 확인·판단할 수 있습니다.

이 도구의 진짜 검증 대상은 사람이 아니라 **데이터 루프**입니다. V1은 목업 없이 곧바로 실전운영으로 시작하므로, 백테스트(104종목 전체)와 실전(조건검색식 후보 한정) 사이에 **모집단 편향**이 존재합니다. wave-double은 모든 추천 후보의 사후 결과를 자동 적재해 실전 승률·PF를 백테스트 기대치와 대조하는 **검증 화면**을 제공하고, 편향의 크기 자체를 관측하는 지표(FR-10)를 함께 제공합니다. 실전 성과가 검증되면 그때 자동매매(V2)를 별도 프로젝트로 개발하는 것이 이 도구의 최종 목표입니다.

> `[NOTE FOR PM]` **대조는 표본이 쌓이기 전까지 판단 근거가 아니다.** 종결 판정 30건 미만에서는 실전 승률·PF를 백테스트 기대치와 나란히 놓지 않는다(FR-9). 실물 자금이 걸린 도구에서 8건짜리 승률을 68%와 비교하는 것은 정보가 아니라 잡음이며, 그 잡음으로 V2 게이트를 여는 것이 이 프로젝트의 가장 큰 실패 모드다.

## 2. Target User

### 2.1 Jobs To Be Done

- **기능적**: 매일/장중 자동으로 매수 후보를 발굴하고, 각 후보의 전략 태깅과 수급 맥락을 한 화면에서 확인한다.
- **기능적**: 백테스트에서 검증한 전략을 실전 종목 발굴에 그대로 적용한다(수동 재현 부담 제거).
- **기능적**: 분산된 수급 데이터(외인/기관/개인/프로그램, 종목·시장)를 자동 집계해 한눈에 본다.
- **검증적**: 실전 추천의 사후 성과를 축적해 백테스트 기대치와 대조하고, "내 전략이 실제로 통하는지"를 데이터로 확인한다. (이 도구의 핵심 JTBD)
- **정서적**: 검증된 엣지를 무료·무인으로 상시 운영해, 놓치는 기회 없이 체계적으로 투자 판단하는 신뢰감을 얻는다.

### 2.2 Non-Users (v1)

- **외부 사용자 전부** — 외부 투자자를 타겟하지 않는 1인용 도구. 인증·멀티테넌트·권한 관리 없음.
- **자동매매 로봇** — V1에서 주문·체결을 자동 실행하는 대상은 아님(실매매는 Neo가 수동 수행).

### 2.3 Key User Journeys

> 단일 사용자·1인 소유 도구이므로 Journey는 간결하게, 핵심 가치 지점(아침 확인, 장중 참고, 사후 검증)에 집중해 작성합니다.

- **UJ-1. Neo가 아침에 "오늘 후보"를 확인한다.**
  - **Persona + context:** 개인 투자자 Neo. 개장 전, 커피 한 잔과 함께 오늘의 매수 후보를 판단한다.
  - **Entry state:** 브라우저로 대시보드 접속(인증 없음/단순). GitHub Actions가 개장 전 일괄 배치를 완료해 당일 후보 모집단·태깅이 갱신된 상태.
  - **Path:** ① 화면 상단에서 **최근 배치 상태와 실행 시각**을 확인한다 ② 오늘 날짜의 태깅(A/B/C)된 후보 목록을 본다 ③ 각 후보의 전략 태그와 수급 힌트를 훑는다 — **개장 전 시점에는 전일 종가 확정 배치의 수급이 근거이며, 당일 수급은 아직 없다** ④ 필요 시 후보별 2일전/1일전/당일 3행 데이터로 판단 근거를 본다 ⑤ 종가 기준 매수 후보를 정리한다.
  - **Climax:** "오늘은 이 종목, A 전략, 수급도 좋다"는 결정을 5분 안에 내린다. 화면에는 왜 노출됐는지가 다중 태그로 보인다.
  - **Resolution:** Neo는 종가에 후보를 수동 매수하며, 이후 UJ-3의 추적에 맡긴다.
  - **Edge case:** 배치가 실패하거나 부분 성공하면 대시보드 상단에 그 사실과 미처리 건수가 명확히 보여, Neo가 "오늘 후보 없음"과 "시스템 고장"을 혼동하지 않고 수동 트리거를 누를 수 있다(FR-6a).

- **UJ-2. Neo가 장중에 수급 흐름을 참고한다.**
  - **Persona + context:** 장중. Neo가 이미 후보를 정했거나 매수 여부를 고민 중이다. 30분 간격 배치가 오전 후보 유지 여부와 수급을 갱신한다.
  - **Entry state:** 대시보드에 장중 30분 간격 배치의 최신값이 반영됨. 각 값에 생성 시각이 병기되어 신선도를 알 수 있다. 최종 추천은 미확정(종가 기준).
  - ⚠️ **장중에 실제로 살아있는 정보는 셋이다** — 시장 전체 수급(FR-5), 가격·거래량·등락율(FR-4), 시그널 유지/소멸(FR-3b). **종목별 수급과 '좋은 수급' 힌트는 장중에 제공되지 않으며 장 마감 후 확정된다**(FR-4 측정 결과). UJ-2는 이 전제 위에서 설계한다.
  - **Path:** ① 장중 배치된 **시장 전체 수급**과 후보별 가격·거래량 흐름을 본다 ② **시그널 소멸/유지 여부**를 확인한다 — 오전에 있던 후보가 사라진 것인지, 배치가 실패한 것인지, 모집단에서 빠진 것인지가 구분되어 보인다(FR-3b) ③ 종목별 수급 힌트는 '판정 불가'로 표시되어 있음을 확인하고, 매수 여부·타이밍을 사전 판단한다.
  - **Climax:** 시장 전체 수급 방향과 시그널 유지 여부를 참고해 종가 매수 타이밍을 조정한다.
  - **Resolution:** 장 종료 후 종가 기준 추천이 확정된다. 장중 배치는 추천을 확정하지 않고 경보·참고 지표로만 동작하며, `candidate_outcome`에 행을 만들지 않는다.

- **UJ-3. Neo가 실전 성과가 백테스트 기대치와 맞는지 검증한다.**
  - **Persona + context:** 일정 기간 실전 운영 후. Neo가 "내 추천이 실제로 통하는지"를 데이터로 확인한다.
  - **Entry state:** 추천후보군 추적페이지(메인 대시보드와 라우트가 분리된 별도 페이지)에 축적된 `candidate_outcome`이 존재.
  - **Path:** ① 추적페이지에서 후보별 TP/SL/TIMEOUT/진행중 결과와 `종결 n건 / 진행중 m건`을 본다 ② 종결 30건 이상이면 실전 승률·PF가 백테스트 기대치와 대조된 지표를 본다(미만이면 '표본 부족' 표시) ③ 이탈 시 **편향 지표(FR-10)**와 함께 원인을 분리 판단한다.
  - **Climax:** 실전 승률·PF가 기대 수준임을 데이터로 확인하거나, 이탈 원인(모집단 편향/시그널 재계산/표본 부족)을 구분해 파악한다.
  - **Resolution:** 검증 결과에 따라 전략 유지·수정 또는 자동매매(V2) 진행 판단의 근거로 삼는다. **(실제 매도·청산 실행은 아님 — 복기·검증만)**

## 3. Glossary

- **거래일(Trading Day)** — 한국거래소(KRX) 정규장이 열리는 날. 판정 원천은 NFR-8에 정의한다. **본 문서의 모든 "N일전"·"N거래일"은 거래일 기준이며 달력일이 아니다.** 모든 시각 표기는 **KST(UTC+9)** 기준이며, GitHub Actions cron 표현식은 UTC로 변환해 기술한다.
- **후보 모집단(Candidate Pool)** — 조건검색식(t1859)이 뽑아낸 종목 집합. CAP-1이 갱신하는 원천 데이터. 전략 태깅은 이 집합 **한정**으로 계산된다(백테스트의 104종목 전체와 구분됨). 상한은 NFR-7.
- **전략 태깅(Strategy Tagging)** — 후보 모집단 한정으로 전략 A/B/C/D/E/F 시그널을 계산해 종목에 부여하는 표시. 다중 태깅 가능(A∩B 등). 태깅된 후보만 대시보드에 노출된다.
- **태깅된 후보(Tagged Candidate)** — 하나 이상의 전략 태그를 가진 후보. V1의 추천 대상.
- **종가 확정 배치(Close Batch)** — 장 마감 후 1회 실행되는 배치. **이 배치의 태깅만 `candidate_outcome`을 생성할 자격을 갖는다.** 장중 배치의 태깅은 참고 표시 전용.
- **수급 판단 힌트(Supply Hint)** — 수급 데이터를 단순 노출하지 않고, 정의된 룰에 따라 후보에 표시하는 판단 힌트. '좋은 수급' = **프로그램매수 + 외인 + 기관이 모두 순매수(> 0)** 상태. 3상태(좋은 수급 / 미충족 / 판정 불가)로 표현한다.
- **3일치 데이터(3-Day Data)** — 후보별 2일전/1일전/당일 3행의 가격·거래량·등락율·수급(외인/기관/개인/프로그램 순매수) 데이터. **거래일 기준** 3행.
- **시장 전체 수급(Market Supply)** — 코스피/코스닥 시장 전체의 수급 집계.
- **사후 결과(Outcome)** — 추천(태깅) 후보의 진입 이후 결과. **4상태**: `TP`(+3% 도달) / `SL`(−3% 도달) / `TIMEOUT`(N거래일 내 미도달, N거래일째 종가 청산) / `OPEN`(진행중). 예외 상태로 `SUSPENDED`(가격 조정 이벤트) · `DELISTED`(상장폐지)를 둔다(NFR-9).
- **TP / SL** — 각각 목표이익 +3%(Take Profit)·손절 −3%(Stop Loss). 백테스트 룰과 동일하게 실전에도 적용한다: **시그널 당일 종가 진입 → 진입 다음 거래일부터 일자별 고가/저가로 판정 → 동일 거래일에 TP·SL 동시 도달 시 SL 우선(보수적), 부등호는 양쪽 등호 포함.**
- **거래비용(Cost)** — 백테스트가 적용하는 **왕복 0.1%**. 실전 손익률도 동일하게 차감한다 → TP 실현 **+2.9%**, SL **−3.1%**. 백테스트 기대치 PF는 이미 이 비용이 반영된 값이다.
- **실전 승률·PF** — `candidate_outcome`으로 계산한 실전 지표. **승률 = (손익률 > 0 인 종결 건수) / (TP+SL+TIMEOUT 건수)**, **PF = Σ(양의 손익률) / |Σ(음의 손익률)|**, 둘 다 비용 차감 후 손익률 기준이며 `OPEN`은 분모에서 제외한다. 승패 판정을 `TP` 상태가 아니라 **손익률 부호**로 하는 것은 백테스트(`metrics/metrics.py:70-72`)와 동일하게 맞추기 위함이다 — TIMEOUT이 양의 손익으로 끝나면 백테스트는 이를 승으로 세므로, 상태 기준으로 세면 두 계산이 어긋난다. 백테스트 기대치(A 68.71%/2.05, B 68.95%/2.08, C 66.00%/1.82)와 대조한다.
- **배치(Run)** — GitHub Actions가 실행하는 파이프라인 한 회. 유형(개장 전 / 장중 / 종가 확정)과 트리거(스케줄/수동)를 기록한다. 이력 테이블명은 `runs`.
- **모집단 편향(Pool Bias)** — 백테스트(104종목 전체)와 실전(조건검색식 후보 한정)의 대상 차이로 발생하는 기대치 이탈. **FR-10이 그 크기를 직접 관측한다.**

## 4. Features

### 4.1 후보 모집단 수집·갱신 (CAP-1)

**Description:** 매 거래일 자동(그리고 프론트엔드에서 수동)으로 조건검색식(t1859)을 실행해 후보 모집단을 수집·갱신한다. 이 기능이 갱신한 후보 모집단이 모든 하위 기능(태깅, 수급, outcome)의 원천이 된다. 실패 시 대시보드에서 명확히 경고한다(FR-6a).

#### FR-1: 후보 모집단 자동 갱신

매 거래일 스케줄(개장 전 일괄 + 장중 30분 간격 + 종가 확정 1회)에 따라 [시스템]이 [조건검색식(t1859)]를 실행해 [후보 모집단]을 [Supabase에] 갱신한다. 실현 UJ-1, UJ-2.

**Consequences (testable):**

- 스케줄 배치가 완료되면 후보 모집단 스냅샷이 저장되고, 저장 건수와 조건검색식 반환 건수가 `runs`에서 대조 가능하다.
- 후보 모집단이 상한(NFR-7, M=150)을 초과하면 절단하되 배치는 실패하지 않는다.
- 배치가 실패하면 FR-6a에 따라 대시보드에 표시되고, 재실행 수단(FR-2)이 제공된다.

#### FR-1a: 후보 모집단 대체 경로 폴백

[시스템]이 [t1859 실패 시] [t1852/t1856 파일저장종목 경로]로 후보 모집단 수집을 재시도한다. 폴백으로 수집된 모집단은 **원천 구분값(`source`: t1859 | t1852 | t1856)**과 함께 저장된다. 실현 UJ-1의 edge case.

**Consequences (testable):**

- t1859가 실패한 배치에서 폴백이 실행되고 `runs.fallback_used`가 기록된다.
- 폴백으로 수집된 후보에서 파생된 모든 태깅·outcome은 원천 구분값으로 필터링 가능하며, FR-9의 실전 승률·PF 집계에서 **원천별로 분리 조회할 수 있다.**
- 폴백 모집단이 t1859 모집단과 동일하다고 가정하지 않는다. 두 원천을 혼합한 지표는 화면에서 구분 표기된다.

#### FR-2: 후보 모집단 수동 갱신

[Neo]가 [프론트엔드 버튼]을 통해 [시간과 무관하게] [배치를 수동 트리거]해 후보 모집단을 갱신할 수 있다. 실현 UJ-1의 edge case.

**Consequences (testable):**

- 수동 트리거가 GitHub Actions `workflow_dispatch`를 정상 호출한다.
- 배치 이력(`runs`)에 트리거 유형(스케줄/수동)이 기록되어 구분 가능하다. (CAP-5와 공유)

### 4.2 전략 태깅 및 후보 확정 (CAP-2)

**Description:** 후보 모집단 한정으로 전략 A/B/C 시그널을 계산·태깅하고, 태깅된 종목만 대시보드에 노출한다. 태깅 로직은 백테스트 룰(backtest-baseline.md)과 일치해야 하며, 다중 태깅이 가능하다. 이는 "왜 이 종목이 노출됐는지"를 다중 태그로 설명하는 핵심이다.

#### FR-3: 전략 A/B/C/D/E/F 시그널 계산 및 태깅

[시스템]이 [후보 모집단 한정]으로 [전략 A/B/C/D/E/F 시그널]을 계산하고, 시그널이 발생한 종목에 [전략 태깅]을 부여한다. 태깅은 다중 가능하며, 태깅 로직은 백테스트 룰과 일치해야 한다. **전략 D(돌파3%기법)·E(익절2%_고정SL5%기법)는 2026-09-04 Correct Course로, 전략 F(각도 가속·이평선 쌍바닥 기법)는 2026-09-07 Correct Course로 A/B/C와 동일한 OR 결합·다중 배지 대상에 편입되었다** — 파라미터·기대치는 `docs/돌파3%기법_추가.md`(후보 A 채택)·`docs/익절2%_고정SL5%기법_추가.md`(문서 그대로 채택)·`docs/각도가속_이평쌍바닥기법_추가.md`(표본 확대형 채택) 및 `backtest-baseline.md` D/E/F 절 참조. 실현 UJ-1.

**Consequences (testable):**

- **골든 픽스처 회귀 대조:** 과거 임의 거래일 1일을 픽스처로 고정하고, 신규 태깅 로직의 A/B/C/D/E/F 시그널 집합을 각각의 참조 구현(A/B/C는 `screen_abc.py`, D/E/F는 신규 코드화된 백테스트 함수) 결과와 대조하는 회귀 테스트를 둔다. **판정 기준은 완전 일치가 아니라 시그널 집합의 Jaccard 유사도 ≥ 0.9**이며, 불일치 종목은 목록으로 출력해 원인을 확인할 수 있어야 한다.
  - **완전 일치를 요구하지 않는 이유(측정된 사실):** 백테스트 데이터(yfinance `auto_adjust=True`, 배당 소급조정)와 실전 데이터(LS `t8410 sujung=Y`, 분할만 조정)는 **기준이 다르다.** 5종목 실측 결과 종가 괴리는 평균 0.5~1.4%, 최대 2.06~6.44%다. 오실레이터 시그널은 임계 교차이므로 이 정도 차이로도 개별 종목의 판정이 뒤집힐 수 있다. **두 원천을 통일하지 않기로 한 결정에 따른 수용된 대가다**(대안: LS로 백테스트 데이터 재수집 — 미채택).
  - 유사도가 0.9 아래로 떨어지면 데이터 기준 차이가 아니라 **로직 결함**을 의심하고 조사한다.
- 하나 이상의 태그를 가진 후보만 후보 목록에 노출된다.
- 다중 태깅(예: A∩B)이 올바르게 표현된다.
- 태깅은 모든 배치에서 계산·표시되나, **`candidate_outcome` 생성 자격을 갖는 태깅은 종가 확정 배치의 결과뿐**이다.
- ⚠️ 재사용 경계: **유니버스 선택·오케스트레이션은 `screen_abc.py`(104종목 고정)와 별도로 신규 구축**하고, **지표 계산 함수와 확정 파라미터는 기존 `backtest.indicator_opt.*` 모듈을 재사용**한다. 경계는 "데이터 로더 교체, 지표 로직 무변경".
- ⚠️ 백테스트 엔진의 숨은 필터 3건(ATR(14) 유효성 게이트, 마지막 봉 시그널 폐기, 최소 보유 1봉)을 실전도 동일하게 반영한다. ATR 게이트의 의도는 `[검증 필요]` — backtest-baseline.md 참조.

#### FR-3a: 시그널 계산용 시계열 이력 확보

[시스템]이 [후보 모집단의 각 종목]에 대해 [전략 A/B/C 계산에 필요한 최소 이력(주봉 %K(20-3) 기준 **최소 120거래일**)]의 [일봉 OHLCV]를 확보한다. 확보 방식은 **Supabase 영속 캐시 + 증분 갱신**을 기본으로 하며, 신규 편입 종목만 전체 이력을 조회한다. 실현 FR-3.

**Consequences (testable):**

- 정상 운영 시 배치당 일봉 전체이력 조회는 **신규 편입 종목 수**에 비례하며, 기존 종목은 1거래일 증분만 조회한다.
- 신규 편입 종목의 120거래일 이력이 **단일 API 콜**로 적재된다(t8410 `qrycnt ≤ 500`).
- 일봉은 LS `t8410`을 **`sujung=Y`(수정주가 적용)**로 수집한다. 이는 분할·무상증자를 조정하되 배당은 조정하지 않는 기준이며, **백테스트 데이터(yfinance, 배당까지 조정)와 기준이 다르다는 사실을 인지하고 수용한다**(FR-3 참조, 괴리 평균 0.5~1.4%).
- 실전 데이터가 백테스트 데이터보다 **오히려 깨끗하다**: `sujung=Y`는 기업행위를 정상 조정하는 반면, 백테스트 데이터에는 미반영 무상증자로 인한 인공 갭이 남아 있다(43종목 114일 — backtest-baseline.md).
- 이력 부족(120거래일 미만 상장) 후보는 태깅 대상에서 제외되고, 그 사실이 후보 상태로 기록된다.

#### FR-3b: 장중 시그널 유지·소멸 표시

[시스템]이 [당일 이전 배치에서 태깅되었으나 최신 배치에서 태깅되지 않은 종목]을 [소멸] 상태로 구분해 표시한다. 실현 UJ-2 ②.

**Consequences (testable):**

- 09:30 배치에서 태깅된 종목이 11:00 배치에서 태깅되지 않으면, 목록에서 사라지지 않고 "소멸" 표시로 남는다.
- **소멸**과 **모집단 이탈**(조건검색식 결과에서 빠짐)과 **수집 실패**(FR-6a 부분성공)가 화면에서 서로 구분된다.
- 태깅 이력은 배치 시점(`run_id`, `tagged_at`) 단위로 보존되어, 당일 태깅 변화 추이를 조회할 수 있다.

### 4.3 후보별 3일치 수급 데이터 (CAP-3)

**Description:** 각 태깅된 후보 종목의 2일전/1일전/당일(거래일 기준) 3행 데이터를 대시보드에 표시한다. Neo가 후보의 수급 흐름을 한눈에 판단할 근거를 제공한다. 실현 UJ-1의 ④.

#### FR-4: 후보별 3일치 수급·가격 표시

[시스템]이 [태깅된 각 후보]에 대해 [2거래일전/1거래일전/당일] 3행의 [가격(종가)·거래량·등락율·외인/기관/개인/프로그램 순매수]를 수집·표시한다. 실현 UJ-1.

**Consequences (testable):**

- 후보마다 3행(거래일 기준)이 정확히 표시된다. 연휴 직후에도 달력일이 아닌 거래일로 3행이 채워진다.
- **당일 행의 가격·거래량·등락율은 장중 배치마다 갱신되나, 당일 수급(외인/기관/개인/프로그램)은 장 마감 후에야 확정된다.** LS가 장중에는 종목별 투자자별 값을 0으로 반환하기 때문이다(아래 측정 결과). 따라서 장중 당일 수급은 **'미확정'으로 표시하고 0을 순매수 0으로 오인하게 두지 않는다.**
- 값의 생성 시각이 화면에 병기된다(FR-6a).
- 종목별 수급·가격은 **`t1702` 1콜**(종가·등락율·거래량·외인·기관·개인)과 **`t1637` 1콜**(프로그램)로 수집한다 — 후보당 2콜.
- 태깅된 후보 전건에 3행이 존재해야 하며, **결측 행이 1건이라도 있으면 해당 배치를 부분실패로 `runs`에 기록하고 대시보드에 결측 종목을 표시**한다.
- 등락율은 **전일 종가 대비**로 계산한다(NFR-9).

> **측정 결과 (2026-08-31 15:22~15:30 KST, 장중 실측).** `t1702`의 당일 행은 `close` 259,000 · `diff` +0.78% · `volume` 13,487,044로 **가격·거래량은 실시간**이나, 투자자별 필드는 **전부 0**이었다(`tjj0008` 개인 0 / `tjj0018` 기관 0 / `tjj0016` 외인 0). 전일 행은 정상 값. `t1637`의 당일 `svolume`/`svalue`도 0. 반면 시장 단위 `t1601`은 장중 실시간 값을 반환했다(FR-5).

### 4.4 시장 전체 수급 화면 (CAP-4)

**Description:** 코스피/코스닥 시장 전체 수급 집계를 화면에 제공한다. 종목별 수급이 시장 전체 흐름 속에서 어떤 의미인지 판단하는 맥락을 제공한다. 실현 UJ-2.

#### FR-5: 시장 전체 수급 표시

[시스템]이 [코스피/코스닥] 시장 전체의 [수급 집계(외인/기관/개인/프로그램)]를 수집·표시한다. 실현 UJ-2.

**Consequences (testable):**

- 시장(코스피/코스닥)별 수급 집계가 대시보드에 표시된다.
- **장중 30분 배치 시점마다 최신값으로 갱신된다** — `t1601`은 종목별 TR과 달리 장중 실시간 값을 제공함이 2026-08-31 실측으로 확인되었다(15:23 시점 개인 +5,733 / 외인 −11,890 / 기관 +517). 생성 시각이 병기된다.
- **종목별 수급이 장중에 비어 있는 동안 시장 전체 수급이 UJ-2의 주된 수급 정보원이 된다.** 이 비대칭을 화면에서 명확히 구분해 표시한다.

### 4.5 자동·수동 트리거 (CAP-5)

**Description:** GitHub Actions 스케줄로 배치를 자동 실행하고, 프론트엔드에서 시간과 무관하게 수동으로도 트리거할 수 있다. 배치 이력(`runs`)에 단계별 성공/실패와 트리거 유형을 기록하고, 그 상태를 화면에 노출해 Neo가 데이터의 신뢰도를 항상 알 수 있게 한다.

#### FR-6: 스케줄 및 수동 배치 실행

[시스템]이 [GitHub Actions 스케줄]로 배치를 자동 실행하고, [Neo]가 [프론트엔드]에서 [수동으로도] 실행할 수 있다. 배치 이력에 결과와 트리거 유형을 기록한다. 실현 UJ-1, UJ-2.

**Consequences (testable):**

- 스케줄이 **개장 전 1회 + 장중 30분 간격 + 종가 확정 1회**로 동작한다. 종가 확정 추천은 장 마감 후 배치에서 생성된다.
- **종가 확정 배치는 16:00 KST(cron `0 7 * * 1-5` UTC)에 실행한다.** 근거: 2026-08-31 실측에서 종목별 투자자별 수급이 **폐장(15:30) 6분 후인 15:36에 채워졌고**(개인 +333,173 / 기관 −2,349,842 / 외인 −2,299 / 기타 +2,018,968, **합계 정확히 0으로 균형**), 16:00은 24분의 안전 여유를 준다. GitHub Actions cron 지연(NFR-8)을 감안한 값이다.
- **빈 수급 적재 방지 가드:** 종가 배치에서 태깅된 후보의 투자자별 필드가 **전부 0이면 아직 채워지지 않은 것으로 보고 해당 배치를 미완료로 처리하고 재시도**한다. **0을 "순매수 0"으로 적재하면 조용히 오염되며 FR-7의 힌트가 전부 틀어진다.**
- 종가 확정 배치는 장 마감 후 실행되므로 당일 종가·거래량이 종가 단일가(15:20~15:30)까지 반영된 최종값이다(실측: 15:22 시점 259,000/13.5M → 확정 260,000/17.0M).
- 수동 트리거가 `runs`에 트리거 유형(스케줄/수동)으로 구분 기록된다.
- `runs`에서 단계별 성공/실패가 조회되어 안정성을 추적할 수 있다.
- 휴장일에는 배치가 no-op으로 조기 종료되고 `runs.skip_reason = holiday`가 기록된다(NFR-8).

#### FR-6a: 배치 상태·신선도 표시

[시스템]이 [메인 대시보드와 추적페이지 상단]에 [최근 배치의 상태(성공/부분성공/실패/휴장일 스킵), 실행 시각(KST), 트리거 유형, 부분성공 시 미처리 항목 수]를 **항상** 표시한다. 실현 UJ-1 edge case, UJ-2.

**Consequences (testable):**

- 최근 배치가 실패한 상태에서 대시보드를 열면 실패 배너와 수동 트리거 버튼(FR-2)이 노출된다. **`runs` 테이블에 행을 넣는 것만으로는 이 Consequence를 만족하지 못한다.**
- 부분 성공 시 수집된 후보는 정상 표시하되, "N종목 수급 미수집" 경고가 함께 표시된다.
- 표시되는 모든 수급·가격 데이터에 그 값을 생성한 배치의 실행 시각이 병기되며, **현재 시각 기준 60분 이상 경과하면 stale로 시각적으로 구분**된다.
- 휴장일에는 "휴장일" 상태가 표시되며 실패로 표시되지 않는다.
- 후보 모집단이 절단된 배치(NFR-7)에서는 절단 건수가 화면에 표시된다.

### 4.6 수급 판단 힌트 (CAP-6)

**Description:** 수급 데이터를 단순 노출에 그치지 않고, 정의된 룰에 따라 후보에 '좋은 수급' 판단 힌트를 표시한다. Neo가 후보를 빠르게 스크리닝하는 데 돕는다. 실현 UJ-1, UJ-2.

#### FR-7: 후보별 '좋은 수급' 힌트 표시

[시스템]이 [당일(최신 배치 시점) 수급] 기준으로, [프로그램+외인+기관 모두 순매수(**> 0**)]인 경우 해당 [태깅된 후보]에 [좋은 수급] 힌트를 표시한다. 실현 UJ-1, UJ-2.

**Consequences (testable):**

- 세 부문이 모두 **> 0**인 후보에 힌트가 표시된다. **순매수 정확히 0(거래 없음 포함)은 '좋은 수급'이 아니다** — 프로그램매매는 0이 흔하므로 `>= 0`으로 두면 거래 없는 종목이 최고 등급으로 표시된다.
- 힌트는 **3상태**로 표현된다: `좋은 수급` / `미충족` / `판정 불가(데이터 없음)`. 데이터가 없어 판정할 수 없는 경우를 미충족으로 표시하지 않는다.
- **장중에는 종목별 수급이 제공되지 않으므로(FR-4 측정 결과) 힌트는 `판정 불가`가 기본값이며, 종가 확정 배치에서만 `좋은 수급`/`미충족`으로 확정된다.** 장중 화면은 "수급 힌트는 장 마감 후 확정"임을 명시한다.
  - ⚠️ 임계값을 `>= 0`으로 두었다면 장중 내내 세 부문이 모두 0이므로 **전 후보가 '좋은 수급'으로 표시**됐을 것이다. `> 0` 확정이 이 결함을 막았다.
- 힌트 룰의 임계값 정의가 한 곳에서 유지·조정 가능하다.

### 4.7 실전 사후 성과 추적·검증 (CAP-7)

**Description:** 모든 추천(태깅) 후보의 사후 결과를 자동 적재·추적하고, 실전 승률·PF를 백테스트 기대치와 대조하는 **검증 화면**을 제공한다. 이는 메인 대시보드와 **라우트가 분리된 추천후보군 추적페이지**로 존재한다. 본 기능은 매수 후 복기·검증 목적이며, 실제 매도·청산 실행은 아니다. V1의 핵심 가치 검증 수단이자 자동매매(V2) 진행 판단의 근거가 된다. 실현 UJ-3.

#### FR-8: 사후 결과 자동 적재

[시스템]이 [**종가 확정 배치에서 태깅된 후보**]에 한해 [진입일(=해당 거래일)·진입가(=**해당 거래일 정규장 종가**)]를 기록하고, 이후 [거래일별 고가/저가/종가]를 수집해 [`TP` / `SL` / `TIMEOUT` / `OPEN`] 상태와 도달일을 `candidate_outcome`에 자동 적재·추적한다. 실현 UJ-3.

**판정 규칙 (백테스트와 동일 — backtest-baseline.md):**

- 진입 **다음 거래일부터** 판정한다. 시그널 당일에는 TP/SL이 발생하지 않는다(최소 보유 1거래일).
- TP = `진입가 × 1.03`, 조건 `고가 >= TP`. SL = `진입가 × 0.97`, 조건 `저가 <= SL`. **부등호는 양쪽 등호 포함.**
- **동일 거래일에 TP·SL이 동시 도달하면 SL 우선**(보수적).
- 손익률은 **왕복 0.1% 비용 차감 후**로 기록한다 → TP `+2.9%`, SL `−3.1%`, TIMEOUT은 실제 종가 손익 − 0.1%.
- **추적 컷오프 N = 30 거래일.** 진입일로부터 30거래일 내 TP/SL 미도달 시 `TIMEOUT`으로 확정하고 30거래일째 종가 손익률을 함께 기록한다. N은 설정값으로 한 곳에서 관리하며, 값을 행(`cutoff_n`)에 함께 저장해 변경 시 과거 outcome을 재계산하지 않는다.

**Consequences (testable):**

- **장중 배치는 `candidate_outcome`에 행을 생성하지 않는다.** 장중 태깅 후 종가에 시그널이 소멸한 종목은 outcome에 남지 않는다.
- `candidate_outcome`은 `(종목코드, 전략, 진입일)`에 **유일 제약**을 가진다. 동일 키 재적재는 갱신이며 신규 행이 아니다.
- 보유 중인 종목이 다음 거래일에 다시 태깅되어도 **새 진입을 생성하지 않는다**(재진입 금지 — 백테스트 `engine.py:112-113`과 동일).
- 진입 후 30거래일이 경과한 미도달 종목은 정확히 `TIMEOUT`이 되며, **이후 배치의 API 조회 대상에서 빠진다.** 따라서 추적 대상 수 P는 항상 `P ≤ (일평균 태깅 후보 수 × 30)`을 만족한다(유계임을 확인 가능).
- 컷오프 N 계산은 휴장일을 건너뛴다(거래일 기준, NFR-8). **거래정지 기간도 N 계산에서 제외된다(NFR-9).** 판정 기준은 달력 경과가 아닌 **실거래 경과일수**(진입 다음 거래일부터 유효 일봉이 존재한 거래일 수)이며, 휴장일·거래정지일 모두 카운트에서 제외된다(2026-09-01 결정, Story 3.7 산식).

**Feature-specific NFRs:**

- outcome 적재는 파이프라인이 **종가 확정 배치마다** 자동 수행하며, 수동 누락 없이 지속 갱신되어야 한다.

#### FR-9: 실전 승률·PF 대조 검증 화면

[시스템]이 [추천후보군 추적페이지]에서 [실전 승률·PF]를 [백테스트 기대치]와 대조해 계산·표시한다. 실현 UJ-3.

**Consequences (testable):**

- **산식:** 승률 = `(손익률 > 0 인 종결 건수) / (TP + SL + TIMEOUT)`, PF = `Σ(양의 손익률) / |Σ(음의 손익률)|`. 둘 다 **비용 차감 후 손익률** 기준이며 `OPEN`은 분모에서 제외한다. 승패는 상태가 아니라 **손익률 부호**로 판정한다(백테스트 `metrics/metrics.py:70-72`와 동일). 화면에 `종결 n건 / 진행중 m건`을 **항상 병기**한다.
- **동일 비용 모델:** 백테스트 기대치 PF는 왕복 0.1%가 반영된 값이므로, 실전도 동일 비용을 적용한다. 동일 입력에 대해 백테스트 계산과 실전 계산이 같은 값을 내는 회귀 테스트가 존재한다.
- **최소 표본 게이트:** 종결 건이 **30건 미만이면 승률·PF 수치 대신 "표본 부족(n/30)"을 표시**하고, 백테스트 기대치와의 대조 판정을 수행하지 않는다.
- **신뢰구간 판정:** 전략별 승률의 **95% 신뢰구간**을 계산·표시하고, 백테스트 기대치가 그 구간 **안/밖** 어디에 있는지 판정한다. 표본 30~50건 구간에서는 고정 임계값보다 신뢰구간이 게이트 판단에 적합하다. (SM-3이 검증하는 대상)
- **이탈 임계값(보조):** 종결 30건 이상에서 승률이 기대치 대비 **±10%p** 밖이거나 PF가 기대치 대비 **±25%** 밖이면 경고로 구분 표시한다. 신뢰구간 판정을 대체하지 않고 보완한다.
- 전략(A/B/C)별 + 전체로 대조 가능하며, 폴백 원천(FR-1a)별로도 분리 조회할 수 있다.
- **컷오프 편향 고지:** `TIMEOUT`은 백테스트에 없는 상태이므로, TIMEOUT 건수와 그로 인한 예상 왜곡(N=30 기준 A ±0 / B PF +0.0125 / C ±0, backtest-baseline.md)을 화면에 함께 표기한다.
- 실제 매도·청산 실행(주문)은 수행하지 않는다. `[NON-GOAL for MVP]`

> `[NOTE FOR PM]` 이 화면의 숫자는 **V2(자동매매) 진행 게이트**의 유일한 근거다. 표본 게이트·비용 모델·컷오프 편향 고지 셋 중 하나라도 빠지면 게이트가 부풀려진 숫자로 열린다. 셋은 함께 구현되어야 하며 개별로 후순위화할 수 없다.

#### FR-10: 모집단 편향 관측 지표

[시스템]이 [추적페이지]에서 모집단 편향의 **크기 자체**를 계산·표시한다. 실현 UJ-3 ③.

**Consequences (testable):**

- 임의 거래일에 대해 "조건검색식 후보 ∩ 전략 시그널"과 "백테스트 유니버스(104종목) ∩ 전략 시그널" 두 집합의 크기·교집합·차집합이 조회된다.
- 백테스트 유니버스 기준 시그널 중 **후보 모집단에 포함되지 않아 추천되지 않은 건수**(기회 누락)가 표시된다. NFR-7로 절단된 종목의 시그널도 여기에 포함된다.
- 실전 승률이 기대치를 이탈했을 때, 편향 지표 추이와 함께 조회되어 **원인 분리**(모집단 편향 / 시그널 재계산 / 표본 부족) 판단이 가능하다.
- 비용 절감을 위해 이 계산은 **일 1회 종가 확정 배치에서만** 수행한다.

## 5. Cross-Cutting NFRs

- **무료 운영 제약(NFR-1)**: 프론트엔드는 Next.js, 로직은 Python(GitHub Actions), DB는 Supabase 무료 플랜만 사용한다. 유료 서비스 의존 금지.
  - **수용하는 대가**: GitHub Actions cron은 정시 실행을 보장하지 않으며(지연·스킵이 정상 조건), Supabase 무료 플랜은 용량 상한과 유휴 시 일시 정지가 있다. 이 대가는 FR-6a(신선도·상태 표시)로 관리하며, 정시성을 전제로 하는 기능은 설계하지 않는다.

- **실행 시간 예산(NFR-2)**: 리포지토리를 **public**으로 운영해 GitHub Actions 사용 분을 **무제한**으로 확보한다. 따라서 월 2,000분 한도는 적용되지 않으며, 실질 제약은 **다음 배치까지의 벽시계 시간(장중 30분)**이다. 배치는 이 창 안에 완료되어야 하며, 초과가 예상되면 부분 성공으로 종료한다(NFR-7).
  - 민감 정보(API 토큰·Supabase 키 등)는 전량 GitHub Secrets로 분리한다(§6.3). **public 운영은 전략 A/B/C의 확정 파라미터와 시그널 로직이 공개됨을 의미하며, 이는 인지된 상태에서 수용한 트레이드오프다.**

- **API 속도 준수(NFR-3)**: LS OpenAPI **TR별** 초당 제한을 준수한다. **후보 팬아웃에 쓰이는 `t1702`·`t1637`·`t8410`은 모두 개인 1건/초**이므로 예산 산정은 1건/초를 기준으로 한다(2건/초는 시장 단위 `t1601` 하나뿐이며 팬아웃에 적용되지 않는다). TR별 토큰버킷 교차 파이프라이닝으로 종목당 실효 시간을 단축할 수 있으나, **TR 간 제한 공유 여부가 문서에 명시되어 있지 않으므로 실측 검증 후에만 적용**한다. 전면 직렬을 최악 케이스 하한으로 삼는다.

- **저장 용량 관리(NFR-4)**: Supabase 무료 용량 내 유지.
  - **보존 대상**: `candidate_outcome`, `bias_metrics`, `daily_ohlcv`(FR-3a 캐시 — 정리하면 매일 재조회가 필요해 역효과), `trading_calendar`, `runs`.
  - **정리 대상**: `supply_3day`의 장중(D0) 이력 스냅샷, 배치별 중간 산출물. 잠정 보존 주기 **90일**로 시작하고 실사용 용량을 보며 조정한다.

- **신뢰성(NFR-5)**: 배치 실패는 FR-6a로 화면에 표시된다. 파이프라인 단계 실패 시 **부분 커밋을 허용하되 각 단계의 완료 여부를 `runs.stage_status`에 단계별로 기록**해 화면이 부분 상태를 정확히 표현할 수 있게 한다. **실패한 단계가 이전 단계의 유효한 데이터를 덮어쓰거나 삭제하지 않는다.**

- **데이터 정확성(NFR-6)**: 대시보드에 표시되는 가격·수급·outcome 수치는 원천(API/계산 룰)과 일치해야 한다. 태깅 계산의 재현성은 **FR-3의 골든 픽스처 회귀 테스트(Jaccard ≥ 0.9)**로 검증한다.
  - ⚠️ **재현성 보장의 한계를 명시한다.** 백테스트와 실전의 수정주가 기준을 통일하지 않기로 결정했으므로(FR-3), 이 NFR이 보장하는 것은 완전 재현이 아니라 **통계적 유사도**다. 개별 종목 단위의 시그널 불일치는 정상 범위 안에서 발생할 수 있으며, 유사도가 0.9 아래로 떨어질 때만 로직 결함으로 취급한다.

- **처리 규모 상한(NFR-7)**: 단일 배치의 처리량에 상한을 두어 벽시계 예산 초과를 방지한다.
  - **후보 모집단 상한 M ≤ 150종목.** 조건검색식 결과가 이를 초과하면 **거래대금 상위**로 결정론적 절단하고, 절단 사실과 건수를 `runs.truncated_count`에 기록하며 화면에 표시한다(FR-6a). 절단된 종목의 시그널은 FR-10의 기회 누락으로 관측된다.
  - outcome 추적 대상은 FR-8의 컷오프(30거래일)로 유계.
  - 예산 초과가 예상되면 배치는 **부분 성공**으로 종료하고 미처리 항목을 `runs.unprocessed_count`에 남긴다. **조용한 누락은 금지한다.**
  - **Consequences (testable):** 조건검색식이 300종목을 반환하는 시나리오에서 배치는 실패하지 않고 150종목으로 절단된 뒤 `runs.truncated_count = 150`을 기록한다.

- **거래 캘린더(NFR-8)**: 시스템은 KRX 거래일 캘린더를 보유하고, **휴장일에는 배치를 no-op으로 조기 종료**한다. 판정 원천은 일봉 응답의 존재 여부이며 그 결과를 `trading_calendar`에 캐싱한다(외부 캘린더 API 의존 없음).
  - 모든 cron은 **UTC로 기술**하고 워크플로 파일에 KST 환산 주석을 병기한다(KST = UTC+9, 한국은 DST 없음. 개장 전 배치는 전일 UTC로 날짜 경계를 넘는다).
  - GitHub Actions 스케줄 지연·스킵을 **정상 조건으로 간주**한다. 개장 전 배치가 개장 시각까지 완료되지 않으면 대시보드는 "미갱신" 상태를 표시한다(FR-6a).
  - 반차 거래일에는 캘린더의 개장/폐장 시각을 기준으로 장중 배치 범위를 산출한다.
  - **Consequences (testable):** 임의 공휴일 날짜로 배치를 실행하면 API 호출 없이 no-op 종료하고 `runs.skip_reason = holiday`가 기록된다. 연휴 직후 배치에서 "2일전/1일전/당일" 3행이 거래일 기준으로 정확히 채워진다.

- **가격 기준·보정(NFR-9)**: 모든 가격 데이터는 **수정주가 기준**으로 통일하며 백테스트 데이터셋과 동일 기준을 사용한다(다르면 그 사실과 영향을 명시). **등락율은 전일 종가 대비**로 정의하고 장중/종가 배치에서 동일 기준을 쓴다.
  - 추적 중 종목에 액면분할·병합·주식배당 등 가격 조정 이벤트가 발생하면 해당 `candidate_outcome`을 **자동 판정에서 제외하고 `SUSPENDED`로 표시**한다. **조용한 오판정을 금지하는 것이 핵심이다** — 분할 미보정 시 진입가(분할 전) 대비 저가(분할 후) 비교로 즉시 SL 오판정된다.
  - **이상 감지는 2단으로 한다(2026-09-01 결정):** ① **1차 신호 = LS `t8410`/`t8451`의 `pricechk`(수정주가 반영 필드, api-map)** — 데이터 원천이 해당 거래일 조정을 직접 보고하면 그 종목은 `SUSPENDED`. 조정 구조의 진실 원천이므로 **갭 크기와 무관하게** 유상증자·주식배당·액면분할을 잡는다. ② **2차 안전망 = 전일 종가 대비 ±30% 초과 갭** — `pricechk` 마커 없이도 발생하는 이상 움직임(미반영 조정·급변) 포착. 임계값(±30%)은 설정값으로 한 곳에서 관리·조정 가능하다. 상장폐지(DELISTED)는 Story 3.9의 별도 감지로 처리한다.
  - 거래정지 기간은 컷오프 30거래일 계산에서 제외한다. 상장폐지 시 `DELISTED`로 종결하고 추적을 중단한다.
  - **Consequences (testable):** ① `pricechk`가 조정을 보고한 종목은 갭이 30% 미만이어도 `SUSPENDED`로 처리된다(유상증자·주식배당의 작은 조정도 놓치지 않음). ② 추적 중 종목의 일봉에 전일 대비 ±30% 초과 갭이 관측되면(마커 유무와 무관하게) 자동 판정하지 않고 `SUSPENDED` 플래그와 함께 알린다. **알림 채널(AD-10 알림 계약, 2026-09-01 결정):** 일상 상태는 pull-only(대시보드 확인), P1급·수신확인 필요한 이벤트(종가 배치 연속 2거래일 실패, SUSPENDED, DELISTED, 백업 실패)만 GitHub Issue로 능동 통지한다. 제3자 push 채널 신규 의존은 두지 않는다(NFR-1).

## 6. Constraints and Guardrails

### 6.1 안전(Safety)

- **실매매 자동화 제외**: 주문·체결은 Neo가 수동 수행하며, V1은 추천(태깅)·추적만 제공한다. 실전 성과 검증 전에 자동매매로 확장하지 않는다. `[NON-GOAL for MVP]`
- **금융·투자자문 금지**: 사실상의 투자 판단을 자동 조언하는 기능은 제공하지 않는다. 도구는 데이터·근거(전략 태깅, 수급 힌트)만 제공하고 최종 판단은 사용자 책임이다.
- **투자 위험 고지(운영)**: 실전 승률이 백테스트 기대치와 다를 수 있음을 FR-9의 표본 게이트·컷오프 편향 고지와 FR-10의 편향 지표로 상시 노출하고, 무분별한 신뢰를 방지한다.

### 6.2 비용(Cost)

- GitHub Actions 분은 public 운영으로 무제한(NFR-2). 감시 대상은 **Supabase 용량**(NFR-4)과 **배치 벽시계 시간**(NFR-7)이다.

### 6.3 데이터 거버넌스

- 단일 사용자 개인 데이터. 실제 매매 계좌·자금 정보는 다루지 않으며(수동 매매, 계좌 연동 없음), 후보·수급·outcome 같은 시장 공개 데이터만 저장한다.
- **리포지토리가 public이므로** 민감 정보(LS API 토큰, Supabase 키 등)는 예외 없이 GitHub Secrets·환경변수로 분리한다. 코드·설정·로그·커밋 이력 어디에도 평문으로 남지 않아야 한다.

## 9. Success Metrics

*스케일 참고: 1인용 실전운영 도구로, 정량 지표는 백테스트 대조·안정성 중심으로 구성합니다.*

**Primary**

- **SM-1 (자동 운영 안정성)**: 롤링 20거래일 기준 **종가 확정 배치 성공률 ≥ 95%, 장중 배치 성공률 ≥ 90%.** 종가 확정 배치가 연속 2거래일 실패하면 P1 사건으로 취급해 즉시 조사한다. Validates FR-1, FR-2, FR-6, FR-6a, FR-8.

**Secondary**

- **SM-4 (모집단 편향 관측)**: 임의 거래일에 대해 후보 모집단 시그널과 백테스트 유니버스 시그널의 교집합·차집합·기회 누락 건수가 조회된다. Validates FR-10.

> 사용 편의성("5분 안에 판단")은 N=1 자기보고라 지표로 기능하지 않으므로 **UX 설계의 인수기준으로 이관**한다.

**Counter-metrics (do not optimize)**

- **SM-C1 (실전 승률/PF 목표 강제)**: 실전 승률·PF가 반드시 백테스트 기대치를 충족하도록 '최적화'하지 않는다. 백테스트와 실전은 대상이 달라(모집단 편향) 기대치를 **관찰·대조**하는 것이 목적이다. SM-3을 게이밍(선택적 추천·결과 제외)하면 검증 루프 가치가 무너진다.
  - **방벽**: 게이밍을 구조적으로 막는 장치는 FR-8의 유일 제약·재진입 금지(중복·선택 적재 차단), FR-9의 진행중 병기·표본 게이트(분모 조작 차단), FR-10의 편향 지표(기회 누락 은폐 차단)다. **경고문이 아니라 이 셋이 실제 방벽이며, 함께 구현되어야 한다.**
- **SM-C2 (절대 수익률 과최적화)**: 대시보드가 수익률 자체를 높이는 도구로 잘못 진화하지 않도록, 핵심 산출물은 '추천 + 사후 대조'에 한정한다.

## 10. Open Questions

1. **백테스트 ATR(14) 유효성 게이트의 의도** — 고정 TP/SL 모드에서 ATR은 쓰이지 않는데도 진입 조건으로 걸려 있어(`engine.py:116`) 각 종목 초기 약 14봉 시그널이 폐기된다. 버그라면 baseline 수치의 재산출 필요 여부를 판단해야 한다. → backtest-baseline.md.
2. **수급 힌트 임계값 세분화** — '좋은 수급'의 초기 정의(`> 0`)는 확정되었으나, 개별 강도(외인 순매수 규모, 프로그램 방향)에 따른 세부 등급은 운영 후 조정 대상.
3. **Supabase 무료 한도 실제 소진** — DB 용량·행 수 한도가 `daily_ohlcv` 캐시 및 `supply_3day` 장중 이력과 결합해 실제로 충분한지 실운영 초기에 검증. → NFR-4의 잠정 보존 주기 90일을 실측으로 조정.
4. **배치 벽시계 시간 실측** — 직렬(1건/초) 기준 추정은 **후보 모집단 M=150 + 태깅된 후보 N**에 대해 `장중 ≈ 1(조건검색) + 150(일봉 증분) + 2N(수급) + 6(시장)` 초, `종가 ≈ 위 + P(outcome 추적)` 초다. **N=30·P=100 가정 시 장중 약 3.6분 / 종가 약 5.3분.** 그러나 **N과 P는 실측 전까지 미지수**이며, 태깅률이 높아 N=100이 되면 장중만 약 6분으로 늘어난다. 30분 창 안에 들어오는지, 그리고 일봉 증분 150콜을 장중마다 반복할 필요가 있는지(장중 시그널 재계산 생략 여부)를 초기 실운영으로 판단한다. → NFR-7, NFR-3(교차 파이프라이닝 실측).
