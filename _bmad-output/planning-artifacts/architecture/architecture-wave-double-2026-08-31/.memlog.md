- (version) Reviewer Gate 최신성 수정: Next.js 16.3.3 Active LTS security release, Node.js 24.17.0 LTS, TypeScript 5.9.3, Playwright 1.62.1, PyArrow 25.0.1, @supabase/ssr 0.12.5.
- (decision) Cold-start package ownership: root pyproject.toml+uv.lock and npm workspaces package.json+package-lock.json이 exact dependency authority다.
- (decision) AD-15 Winner 계약: logical run당 하나의 canonical attempt만 outcome 생성 자격을 가진다. publication transaction이 logical_runs.canonical_attempt_run_id를 단일 행으로 선택하고, outcome 생성 함수는 후보가 해당 canonical_attempt_run_id에 속하고 그 run이 success 출판 상태인지 FK/constraint로 검증한다. canonical 선택 기준: 1) success 상태 우선, 2) 동일 상태면 fence_token 최대(최신 시도), 3) 동일하면 started_at 최대, 4) 동일하면 run_id 최대. partial close attempt는 outcome을 생성하지 않는다.
- (decision) AD-16 Provenance 계보: 후보 source가 outcome·metrics까지 손실 없이 흐른다. candidates.source (t1859|t1852|t1856) → candidate_tags (FK로 source 상속) → candidate_outcome (canonical attempt 후보만 생성, source 보존) → bias_metrics (원천별 교집합/차집합/기회누락 별도 slice) → read model metrics view (원천별 승률/PF/표본수 별도 노출). 모든 단계에서 source 컬럼이 손실 없이 전파되며, *_by_source 표준화된 뷰/함수명으로 혼합/원천별 집계를 구분한다. runs.fallback_used는 실행 요약일 뿐 row-level provenance를 대체하지 못한다. 다음 테이블에 source TEXT NOT NULL REFERENCES candidates(source) 필수: candidate_tags, candidate_outcome, bias_metrics, candidate_source_contrib.
- (decision) AD-17 운영 복구 계약: RPO/RTO/backup/교정 절차를 provider 선택 조건으로 고정한다. V1 배포 전 provider acceptance contract로 확정: 1) RPO ≤ 1시간, RTO ≤ 4시간, 2) Supabase PITR 활성화 필수(또는 동등한 self-managed backup 검증), 3) migration 전 자동 restore point 생성, 4) 정기 restore drill(분기 1회) 및 복구 책임자/절차 문서화, 5) 복구 후 current_complete_run_id 포인터 재설정 및 GitHub schedule 재개 순서 명시. immutable outcome 오류는 원행 수정이 아닌 감사 가능한 outcome_correction event(원래 outcome_id, 사유, 수정치, 승인자)로만 복구하며 집계 제외/대체 규칙으로 처리한다. 대량 오염 시 restore vs correction 선택 기준: 영향 행 수 > 1% 또는 다일간 누적이면 restore, 그 외 correction. LS 원문 응답 영구 보존 안 하면 재현 가능한 최소 input_hash/adapter_version/cutoff_ts를 run_attempts artifact 컬럼에 남긴다.
- (decision) AD-18 Dispatch 멱등성: DB 영속 키 + 요청 해시 + outbox로 dual-write gap을 닫는다. /api/runs/dispatch는 DB 영속 테이블 dispatch_idempotency(sub, route_contract, idempotency_key PK, request_hash, status, created_at, completed_at, github_dispatch_id, payload_jsonb)를 쓴다. canonical request hash(SHA-256)를 함께 저장해 같은 key+같은 hash만 replay(기존 github_dispatch_id 반환), 같은 key+다른 hash는 409 Conflict로 거부한다. 보존 TTL은 GitHub/API 최대 retry 창(24h)보다 긴 7일, 상태는 pending→succeeded|failed|unknown 머신으로 관리. DB record 생성과 GitHub dispatch 사이의 dual-write gap은 outbox 테이블(dispatch_outbox) + 별도 reconciler(1분 주기)로 닫는다. reconciler는 pending 초과 TTL을 unknown으로 올리고 GitHub API로 실제 dispatch 상태를 조회해 동기화한다. pg_cron 확장 또는 전용 Cloud Run Job/Function으로 배포, 헬스체크 엔드포인트 제공.
- (decision) AD-3 강화: 상태 저장 shape와 stale worker fencing을 강제한다. 최소 shared shape 고정: logical_runs(logical_run_key PK, canonical_attempt_run_id, current_complete_run_id, latest_partial_run_id, ...), run_attempts(run_id PK, logical_run_key FK, attempt_no UNIQUE per key, fence_token BIGINT GENERATED ALWAYS AS IDENTITY, status, started_at, finished_at, trigger, batch_kind, stage_status JSONB, unprocessed_count, truncated_count, fallback_used, ...), run_stages(run_id FK, stage PK, status, result_code, retryable, unprocessed_count, duration_ms, started_at, finished_at, ...). orchestrator만 위 테이블을 변경하며, GitHub Actions concurrency: {group: logical_run_key, cancel-in-progress: true}와 DB advisory lock으로 같은 논리 키를 직렬화한다. attempt 시작 시 DB sequence(fence_token BIGINT GENERATED ALWAYS AS IDENTITY)로 단조 증가 토큰을 발급하고, 모든 stage write/publish RPC는 현재 fence_token과 canonical_attempt_run_id 자격을 검사한다. advisory lock만을 stale-write 방지 수단으로 사용하지 않는다. 각 stage writer는 자기 테이블과 stage result만 idempotent upsert한다. 상태 전이는 expected status를 받는 전용 RPC/CAS만 허용하고 JSON read-modify-write 같은 임의 mutation을 금지한다.
- (decision) AD-9 강화: 동일 (ticker, strategy)의 미종결 outcome은 최대 1개로 제한한다. candidate_outcome에 partial unique index CREATE UNIQUE INDEX candidate_outcome_open_unique ON candidate_outcome (ticker, strategy) WHERE status = 'OPEN'로 강제한다. 종가 태깅 단계 생성 transaction은 (ticker, strategy)를 잠그고 기존 OPEN이 있으면 새 진입을 폐기하므로 보유 중 재진입과 청산일 당일 재진입을 금지한다. projection은 entry_candidate_id, created_run_id, last_observation_id를 보존한다. terminal TP/SL/TIMEOUT은 이후 observation으로 바뀌지 않는다. SUSPENDED(가격 조정 의심), DELISTED(상장폐지)는 자동 판정에서 분리하고 수동 감사 없이는 종결 지표에 포함하지 않는다. outcome 생성 자격은 AD-15의 canonical close attempt 후보만 가진다.
- (decision) AD-6 강화: M=150 결정론적 절단 규칙과 관측 계약을 고정한다. screen stage에서 모집단이 150을 넘으면 거래대금 내림차순, 종목코드 오름차순으로 결정론적 상위 150개만 선택한다(안정적 tie-break). 절단은 실패/미처리가 아닌 관측 가능한 정상 경계이며 runs.truncated_count에 제외 수를 기록한다. 절단된 종목의 시그널은 FR-10 기회 누락에 포함되어 bias_metrics로 이어진다. 같은 입력이면 동일 후보가 선택돼야 한다.
- (decision) AD-5 강화: 일봉 캐시 스테이지(태깅 이전 필수)의 수명주기·최소 이력 계약을 고정한다. 소유 모듈: apps/batch의 ohlcv_cache stage가 daily_ohlcv 테이블을 독점 소유한다. readiness gate: 태깅 실행 전 대상 종목 모두 >=120 trading days 충족하는지 검증, 미충족 시 stage error로 승격해 태깅을 막는다. 갱신 전략: 기존 종목은 1거래일 증분(t8410 1일치), 신규 편입 종목만 전체 이력 단일 콜로 적재(qrycnt≤500 내). 보존 예외: daily_ohlcv는 NFR-4의 '일봉 정리' 대상이 아니다 — 장기 보존 대상이며, 정리 대상은 배치별 중간 스냅샷만이다. CI Enforcement: GitHub Actions job backtest-parity 필수: 골든 픽스처 실행 → 전략별 신호 집합 Jaccard 계산 → 0.9 미만 시 fail → 아티팩트(jaccard-report.json) 업로드. main 브랜치 보호 규칙에 required status check로 등록.
- (version) Reviewer Gate 최신성 수정: Node.js 24.20.0 LTS (2026-08-26 release, npm 11.19.0). 기존 24.17.0에서 최신 patch로 갱신. react-dom 19.2.8 Stack 표 추가(React와 동일 버전 pin). TypeScript 5.9.3 선택 근거: Next.js 16 지원 범위(5.1+) 내 호환성 우선, TS7/Next 호환성 검증 후 승격 시 revisit.
- (decision) AD-15 강화: canonical_attempt_run_id는 반드시 success 상태인 attempt만 선택한다. fence_token 순서는 success attempt 사이에서만 적용한다. partial/failed attempt가 max fence_token을 가져도 canonical이 될 수 없다. publication transaction이 logical_runs.canonical_attempt_run_id를 선택할 때 status='success'인 행만 후보로 고려한다.
- (decision) AD-19 Provenance 무효화: non-canonical attempt의 행을 정리한다. canonical publish transaction이 실행될 때, 해당 logical_run_key의 이전 attempt(row_id가 다른 attempt_no)에 속한 candidate_tags, candidate_outcome, bias_metrics, candidate_source_contrib 행을 삭제하거나 superseded_by_run_id로 마킹한다. 이렇게 하면 retry winner의 source(t1852)가 bias_metrics 등에서 이전 partial attempt의 source(t1859)와 섞이지 않는다. outcome_observations은 append-only 원장이므로 superseded_by_run_id로 마킹만 하고 삭제하지 않는다.
- (decision) AD-3 추가: cross-attempt stage 중복 방지. logical run 재시도 시작 시(새 attempt_no), orchestrator는 이전 attempt의 run_stages 행을 삭제하거나 status='superseded'로 마킹한다. 또한 logical_runs.latest_partial_run_id를 NULL로 리셋한다. 이렇게 하면 stale worker가 이전 attempt의 stage row를 쓰지 못하도록 하고, read model join 시 단일 attempt의 stage만 보이게 한다. unique constraint (logical_run_key, stage)는 canonical stage view에만 적용하고, 물리 테이블 run_stages는 (run_id, stage) PK를 유지하되 status='superseded' 필터로 조회한다.
- (decision) AD-17 강화: restore_epoch로 PITR 복구와 correction 이벤트 구분. outcome_correction event에 restore_epoch 컬럼 필수(초기값 0, PITR restore 시마다 1 증가). metrics view와 bias_metrics 집계는 WHERE restore_epoch = (SELECT MAX(restore_epoch) FROM outcome_corrections)로 최신 epoch만 포함한다. restore drill 시 staging DB의 restore_epoch를 프로덕션과 동일하게 설정해 double-count 방지. 대량 오염 복구 시 restore_epoch 증가와 correction 이벤트 생성을 동일 transaction에서 수행한다.
- (decision) AD-18 강화: idempotency key에 logical_run_key 포함으로 GitHub concurrency와 정합. dispatch_idempotency PK를 (sub, route_contract, idempotency_key)에서 (logical_run_key, sub, route_contract, idempotency_key)로 변경. logical_run_key는 close/premarket의 (trading_day, batch_kind, final), intraday의 (trading_day, batch_kind, KST 30-minute slot)이다. 이렇게 하면 서로 다른 사용자가 같은 logical run을 dispatch하더라도 첫 번째만 성공하고 나머지는 replay(기존 github_dispatch_id 반환)된다. 수동 실행은 논리 실행 키당 단일 사용자/단일 시도로 제한됨을 문서화한다. GitHub Actions concurrency group은 logical_run_key를 그대로 사용한다.

- (decision) AD-20 Publication Authority: Orchestrator exclusively runs publication transaction at success attempt commit; no external publisher.
